# Timeline Grid

사진 여러 장에 각각 시각과 문구를 붙여, 하루의 흐름을 담은 타임라인 콜라주를 만들어 주는 웹 앱.
시각은 사진의 EXIF 촬영 시각에서 자동으로 채워진다.

3×2 여섯 컷이 한 장(3077×4096)이고, 사진이 6장을 넘으면 자동으로 다음 장으로 넘어간다.
업로드·합성·저장이 전부 브라우저 안에서 끝나므로 사진은 어디로도 전송되지 않는다.

## 레이아웃

레이아웃은 눈대중이 아니라 원본에서 측정했다.
[instagram.com/p/Daz6IEyEpT5](https://www.instagram.com/p/Daz6IEyEpT5/) 캐러셀 12장(각 3077×4096)을
내려받아 흰 행·열을 스캔한 결과, 12장 전부 아래 값에서 일치했다 — 사람이 매번 배치한 게 아니라 고정 템플릿이다.

| 항목 | 실측값 (3077px 기준) |
|---|---|
| 캔버스 | 3077 × 4096 |
| 사진 행 top | 0 / 1347 / 2695 (pitch 1347.5) |
| 사진 셀 | 1538.5 × 1032, 좌우 여백 0, 열 간격 0 |
| 캡션 밴드 중심 | 행 top + 1193 (= 사진 하단 + 161) |
| 캡션 | Tinos 45px, 행간 50px, 열 중앙 정렬 |
| 캡션 잉크 상자 | 445 × 42 (`04:56, Thursday, July 09`) |

`timeline.js`의 `SPEC`이 이 값들을 캔버스 폭 대비 비율로 들고 있다.

## 캡션 폰트

캡션 폰트는 7종에서 고를 수 있고, 그중 넷은 한글 글리프를 가진다.

| 폰트 | 한글 | 정규화 크기 |
|---|---|---|
| Tinos (기본 · 원본) | | 45.3px |
| EB Garamond | | 47.8px |
| Lora | | 40.5px |
| 본명조 Noto Serif KR | O | 39.2px |
| 고운바탕 Gowun Batang | O | 41.9px |
| 나눔명조 Nanum Myeongjo | O | 41.4px |
| 본고딕 Noto Sans KR | O | 40.4px |

폰트별 상수 표는 두지 않는다. 렌더할 때마다 `ctx.measureText()`로 기준 문자열(원본 첫 컷 캡션
`04:56, Thursday, July 09`)의 잉크 폭과 ascent/descent를 실측해서 세 가지를 유도한다.

- **크기** — 잉크 폭이 원본의 445px가 되도록 맞춘다. Tinos는 원래 값인 45px 부근으로 돌아온다.
- **위치** — 실측 ascent/descent로 baseline을 역산해, 잉크 밴드 중심을 행 top + 1193에 놓는다.
- **행간** — 잉크 높이 + 0.2em. 원본의 50px는 Tinos 잉크 0.911em에서 나온 이 규칙의 특수해다.
  50px로 고정하면 잉크가 1.08em인 본명조는 두 줄 간격이 1.4px까지 좁아진다.

기준 문자열을 고정하는 것이 핵심이다. 캡션마다 실측하면 한 행에 나란히 놓인 영문 캡션과 한글
캡션의 baseline이 서로 어긋난다. 원본 12장이 전부 같은 위치였다는 건 고정 baseline이었다는 뜻이다.
한글은 디센더가 없어 잉크 중심이 2~4px 위로 올라가는데, 모든 캡션이 같이 올라가므로 정렬은 유지된다.

한글 폰트의 Google Fonts CSS는 58~98KB(한글이 unicode-range 서브셋 90~124개로 쪼개져 있다)라서
`<link>`는 폰트를 고를 때 주입하고, `document.fonts.load(spec, text)`에 캡션 텍스트를 넘겨
필요한 서브셋만 내려받는다. 캔버스는 CSS처럼 글리프별 fallback을 해주지 않으므로 이 순서가 중요하다.

(정규화 크기는 Chrome / macOS 실측값이다. 폰트 렌더러에 따라 소수점은 조금 달라진다.)

## 미리보기 해상도

미리보기 캔버스는 CSS로 컨테이너 폭까지 늘어나므로(`width: 100%`), 비트맵은 **화면에 실제로 찍히는
디바이스 픽셀 수**여야 한다. `previewWidth(cssW, dpr)`가 그 값을 만들고, 컨테이너 폭은 캔버스를
DOM에 넣은 뒤 한 번만 잰다(모든 장이 같은 폭이다).

고정 620px이던 시절 Chrome/macOS DPR 2에서 잰 값:

| 창 | 캔버스 CSS 폭 | 620px 비트맵의 확대율 | 현재 비트맵 | 현재 확대율 |
|---|---|---|---|---|
| 데스크톱 (`.wrap` 1040 상한) | 962 | 3.10× | 1924 | 1.000× |
| 좁은 창 | 622 | 2.01× | 1244 | 1.000× |
| 모바일 375px | 313 | 1.01× | 626 | 1.000× |

CSS 폭만 보면 1.0배 근처라 멀쩡해 보이는 게 함정이었다. 흐림은 CSS 크기가 아니라 HiDPI에서 왔다.

폭이 3.1배가 되면 픽셀 수는 9.6배지만, 문구를 한 글자 칠 때마다 도는 `drawPages()`는
사진 12장(2장 분량) 기준으로 이 정도다 — 11회 중앙값, `getImageData()`로 래스터화를 강제한 값.

| 비트맵 폭 | 핸들러 동기 시간 | 래스터화까지 |
|---|---|---|
| 620 (이전) | 0.9ms | 2.2ms |
| 1924 (데스크톱) | 1.7ms | 4.9ms |
| 626 (모바일) | 1.2ms | 2.8ms |

한 프레임(16.7ms) 안에 여유 있게 들어와서 디바운스도, 입력 중 저해상도 렌더도 넣지 않았다.
DPR 3 폰이라도 313 × 3 = 939px로 데스크톱보다 작아서 모바일 상한도 두지 않았다.
상한은 내보내기 폭(3077)에만 걸어 둔다. 컨테이너가 962 CSS px를 넘지 않으므로 DPR 3.2부터 닿는다.

캡션 위치는 폭을 바꿔도 그대로다. 620 / 1282 / 1924 / 3077에서 렌더한 뒤 흰 행 스캔으로 잉크 밴드를
재고 3077 기준으로 환산했을 때, 밴드 중심과 `행 top + 1193` 사이의 오차는 Tinos가 ±2px,
본명조 + 한글 캡션이 −2~−6px으로 **모든 폭에서 같았다.** 한글 쪽 상수 오프셋은 기준 문자열이 라틴
문자열로 고정돼 있어 생기는 원래 성질이고(위 "캡션 폰트" 참고), 해상도와는 무관하다.

## 사진 읽기

사진을 고르면 `addFiles()`가 파일마다 `createImageBitmap()`으로 디코딩하고 EXIF 앞머리를 읽는다.
예전에는 그 둘을 `for` 루프 안에서 `await` 했다. 그래서 **디코딩이 한 번에 한 장씩** 돌았고,
`refresh(true)`가 루프 밖에 있어서 **마지막 한 장이 끝날 때까지 화면이 완전히 비어 있었다.**

읽기를 전부 시작해 놓고 파일 순서대로 기다린다. 시작이 먼저이므로 디코딩은 브라우저 이미지
스레드에서 나란히 돌고, 기다리는 순서가 파일 순서이므로 카드 순서는 고른 순서 그대로다.
그리고 한 장이 도착할 때마다 그린다.

아이폰 12MP 사진 12장(4032×3024, 합계 55MB) 실측 — Chrome 150 / macOS, 14코어, DPR 2,
같은 탭에서 두 버전을 연달아 5회씩, 중앙값. `getImageData()`로 래스터화를 강제했다.

| | 이전 | 지금 |
|---|---|---|
| "읽는 중" 표시가 뜨기까지 | (없음) | **2ms** |
| 첫 사진이 화면에 | 3,049ms | **817ms** |
| 12장 전부 | 3,049ms | **997ms** |
| 래스터화까지 | 3,061ms | **1,001ms** |

이전에는 첫 사진과 마지막 사진이 같은 시각이다. 그게 3초 동안 아무 일도 안 일어나는 것처럼
보이던 이유고, 화면 갱신이 아니라 **기다리는 방식**이 문제였다는 증거다. 구간별로 보면:

| 구간 | 순차 | 병렬 |
|---|---|---|
| `createImageBitmap` 12장 | 2,787ms | **857ms** |
| EXIF 앞 128KB 읽기 12장 | 8ms | 3ms |

비용은 사실상 전부 디코딩이다. EXIF는 반올림 오차 수준이다.

**`resizeWidth`로 비트맵을 줄이는 건 오히려 느리다.** 12MP를 그대로 들고 있는 게 메모리
(12장이면 558MB)로는 아깝지만, Chrome에서 리사이즈를 걸면 같은 12장 병렬 디코딩이 이렇게 된다.

| 옵션 | 시간 |
|---|---|
| 리사이즈 없음 | **825ms** |
| `resizeWidth: 3077, pixelated` | 1,307ms |
| `resizeWidth: 3077, low` | 1,787ms |
| `resizeWidth: 1924, medium` | 3,590ms |
| `resizeWidth: 3077, high` | 4,356ms |

게다가 상한을 걸면 셀당 4배 줌에서 쓸 소스 픽셀이 줄어 미리보기와 내보내기가 같이 흐려진다.
빠르지도 않고 화질도 잃는 쪽이라 넣지 않는다.

### 많이 골라도 터지지 않는다

읽기를 한꺼번에 시작하니 디코딩 메모리도 한꺼번에 몰리는 것 아니냐 — 12·24·36·48장으로 재 봤다.
같은 12장을 반복해 배치를 늘렸으므로 디코딩 작업량과 비트맵 메모리는 실제 48장과 같다.

| 장수 | `createImageBitmap` 동시 실행 | 장당 | 실패 |
|---|---|---|---|
| 12 | 1,972ms | 164ms | 0 |
| 24 | 2,688ms | 112ms | 0 |
| 36 | 3,333ms | 93ms | 0 |
| 48 | 4,082ms | 85ms | 0 |

장당 비용이 오히려 **내려간다**. 48개를 한 번에 요청해도 48장이 동시에 디코딩되는 게 아니라
브라우저의 이미지 디코드 스레드 풀에 줄을 서기 때문이다. 즉 상한은 이미 브라우저 안에 있다.
직접 상한을 걸어 봐도 총 시간은 그대로거나 나빠진다 — 48장 기준 무제한 3,504ms, 8개 3,359ms,
4개 3,494ms, 2개 5,062ms. 그래서 **동시 실행 개수 제한은 넣지 않는다.**

48장 배치에서 탭이 죽거나 사진이 빠지는 일은 없었다(카드 48장, 실패 0, 미처리 거절 0).
렌더러 RSS는 3.2GB에서 7.7GB까지 올라갔다가 회수된다.

사진이 한 장 도착할 때마다 `refresh(true)`가 `drawPages()`를 돌려 **모든 장의 캔버스를 처음부터
다시** 그린다. n장이면 페이지 렌더가 n번이니 제곱이다. 그래서 재 봤다 — `drawPages()` 한 번의
비용은 캡션 로케일을 바꿔 `refresh()`만 돌린 값이고, `getImageData()`로 래스터화를 강제했다.

| 사진 | 장 | `drawPages()` 1회 | 장당 |
|---|---|---|---|
| 6 | 1 | 1.7ms | 0.28ms |
| 12 | 2 | 2.6ms | 0.22ms |
| 24 | 4 | 4.0ms | 0.17ms |
| 36 | 6 | 6.6ms | 0.18ms |
| 48 | 8 | 56.7ms | 1.18ms |

제곱이긴 한데 상수가 작다. 12장 배치가 무는 총액은 다 합쳐 **14ms 남짓, 전체의 1.5% 미만**이다.
48장에서 한 번에 57ms로 뛰는 건 캔버스 8장(각 1924×2561)이 GPU 메모리를 밀어내기 시작하는
지점이고, 그래도 배치 총액은 1초 대다. 사진이 도착할 때마다 눈앞에서 그림이 자라는 값으로는
싸다. **도착한 장만 다시 그리는 최적화는 넣지 않는다.**

`ImageBitmap.close()`도 마찬가지다. 카드를 지우거나 전체를 비울 때 비트맵을 명시적으로 닫지
않는데, 12장을 열 번 만들면서 닫는 쪽과 참조만 버리는 쪽을 비교하면 1,177ms 대 1,209ms로
차이가 없다. Chrome이 알아서 회수한다. **`close()` 호출도 넣지 않는다.**

(측정 중 배치를 반복할수록 느려지는 것을 본다면 앱이 아니라 기계를 먼저 의심할 것. 같은
코드가 load average 7인 머신에서 416ms와 561ms로 갈렸다. 아래 "촬영 시각" 위의 주의와 같은
종류의 함정이다.)

### 카드 썸네일

카드의 `<img>`는 78×52다. 예전에는 그 자리에 원본 파일의 object URL을 그대로 물렸다. 78×52 한
칸을 채우려고 브라우저가 **12MP를 통째로 한 번 더 디코딩**했다는 뜻이다. 디코딩된 비트맵은 이미
손에 있으므로, 그걸 156px(78의 2배, DPR 2 화면이 요구하는 값)로 한 번 줄여 data URL로 넣는다.
장당 4KB고, 크롭은 원래 있던 `object-fit`이 한다. 카드 DOM과 CSS는 그대로다.

12장 기준, 두 경로를 같은 루프 안에서 번갈아 6라운드 — 부하가 양쪽에 똑같이 걸리도록:

| | 중앙값 | 라운드별 |
|---|---|---|
| 가진 비트맵을 156px로 (지금) | **5ms** | 5, 5, 5, 5, 5, 5 |
| 원본을 다시 디코딩 (이전) | **534ms** | 532~540 |

덤으로 object URL이 붙잡던 파일 바이트(12장이면 55MB)가 풀린다. `URL.revokeObjectURL` 호출
두 군데도 같이 사라졌다 — 되돌려 줄 것이 없어졌기 때문이다.

**단, 534ms는 `drawImage()`로 디코딩을 강제해서 잰 값이다.** 보이는 탭에서는 브라우저가 `<img>`를
메인 스레드 밖에서 디코딩하므로, 사용자가 실제로 느끼는 멈춤은 이보다 작다(한 장씩 재면 `load`를
기다리는 사이에 이미 디코딩이 끝나 있어 0ms로 읽힌다). 확실한 것은 12MP 디코딩 12번어치의 CPU와
55MB가 사라졌다는 것이고, 그것이 메인 스레드에서 얼마였는지는 **측정하지 못했다.**

캔버스 옵션은 아무것도 주지 않는다. `willReadFrequently: true`는 4ms 대 10ms, `imageSmoothingQuality`
는 기본값 대 `high`가 4ms 대 5ms다. 78px 썸네일에서 둘 다 주석 값을 못 한다.

### 못 여는 포맷

`createImageBitmap()`도 `<img>` 폴백도 거절하는 파일이 있다. 예전에는 그 거절이 `addFiles()`를
그대로 뚫고 나가서 **배치 전체가 조용히 죽었다** — 이미 읽은 사진들까지 `refresh(true)`를 못 받고
사라졌고, 콘솔에 `EncodingError` 한 줄만 남았다. 사용자 입장에서는 "느리다"와 구분되지 않는다.

지금은 그 파일만 건너뛰고 나머지는 정상으로 간다. 건너뛴 파일은 업로드 상자 아래에
`skippedNote()`가 만든 문구로 이름과 함께 뜬다.

**`image/` 필터도 없앴다.** `addFiles()`는 예전에 `f.type.startsWith('image/')`로 먼저 걸렀다.
그 필터에 걸린 파일은 카드도, 안내도, 아무것도 남기지 않고 사라졌다 — 위에서 고친 것과 같은
버그가 한 층 위에 하나 더 있었던 셈이다. 게다가 `file.type`은 OS가 확장자를 보고 붙여 주는
값이라 빈 문자열인 경우가 있고, 그러면 **멀쩡한 JPEG가 조용히 버려진다.** 지금은 고른 것을
전부 읽어 보고, 못 읽은 것은 위와 똑같이 이름을 말해 준다.

| 고른 것 | 이전 | 지금 |
|---|---|---|
| `notes.txt` + JPEG 2장 | 카드 2장, 안내 없음 | 카드 2장 + `notes.txt` 안내 |
| `file.type`이 빈 JPEG + JPEG 2장 | **카드 2장** (한 장 증발) | 카드 3장 |
| `notes.txt` 한 장만 | 아무 일도 안 일어남 | 안내 |

문구에 이름을 몇 개까지 넣을지는 제한하지 않았다. 사진 아닌 파일이 잔뜩 섞인 폴더를 통째로
끌어다 놓으면 그만큼 길어진다는 뜻이다. 실제로 그렇게 쓰는 것을 보기 전에 자르지 않는다.

가장 흔한 경우가 **HEIC**다. iPhone 기본 포맷인데 WebKit 말고는 디코더를 가진 엔진이 없다.
Chrome/macOS에서 `.heic`는 `image/heic`으로 들어와 디코딩에서 걸린다.
그래서 HEIC일 때는 이름만 알려주는 대신 실제로 해결되는 안내를 붙인다 — 설정 > 카메라 > 포맷을
'높은 호환성'으로 두거나 JPEG로 바꿔 올리는 것. HEIC 판별은 `file.type`이 아니라 파일명 확장자로
한다(브라우저가 확장자에 무슨 타입을 붙일지는 OS가 정하고, 빈 문자열인 경우도 있다).

HEIC 1장을 섞은 3장짜리 배치 실측 — 위치와 무관하게 결과가 같다.

| | 이전 | 지금 |
|---|---|---|
| `[HEIC, JPEG, JPEG]` | 카드 0장 | JPEG 2장 + 안내 |
| `[JPEG, HEIC, JPEG]` | 카드 0장 | JPEG 2장 + 안내 |
| `[JPEG, JPEG, HEIC]` | 카드 0장 | JPEG 2장 + 안내 |

**HEIC 디코더는 넣지 않는다.** libheif-js(WASM)를 실제로 붙여서 재 봤다: 4032×3024 HEIC
한 장이 666ms(파싱 22ms + 픽셀 변환 644ms), 12장이 **12,027ms**다. `display()`가 동기 WASM이라
메인 스레드에서 돌리면 그 12초 동안 UI가 얼고, 안 얼리려면 Worker가, 코어를 쓰려면 Worker N개와
WASM 인스턴스 N개가 필요하다. 페이로드도 `libheif.wasm` 1,034KB + 글루 81KB로 이 앱 전체(51KB)의
22배다. 고친 뒤의 네이티브 경로(857ms)보다 14배 느린 것을 1.1MB와 빌드 단계를 주고 사는 셈이라
하지 않는다. 정작 아이폰 사진이 아이폰·맥 Safari에서 열릴 때는 이미 네이티브로 디코딩된다.

## 촬영 시각

카드의 시각 기본값은 사진에 박혀 있는 EXIF 촬영 시각이다. 파일 수정 시각(mtime)을 쓰면
AirDrop·다운로드·복사를 거친 사진이 전부 "옮긴 시각"이 된다 — 실제로 Hugo 테스트데이터의 카메라
JPEG 7장은 mtime이 죄다 `go mod`가 내려받은 2024-12-01이고, EXIF 쪽은 2010~2022로 흩어져 있었다.
12장을 손으로 고치는 건 이 앱의 요점을 무너뜨리므로, 읽을 수 있으면 읽는다.

폴백 순서는 `DateTimeOriginal`(0x9003, 셔터가 열린 시각) → `DateTimeDigitized`(0x9004, 카메라에서는
같은 값이고 스캔본은 이쪽만 가진다) → IFD0의 `DateTime`(0x0132, 편집 시각이지만 그래도 픽셀과 같이
따라다닌다) → 파일 mtime. 파서는 `timeline.js`의 `exifDateTime()`이고, `ArrayBuffer`(또는 그 뷰)를
받아 `Date | null`을 돌려주는 순수 함수다. 의존성은 없다.

- **읽는 것** — JPEG APP1 세그먼트 안의 TIFF 블록. 마커 체인을 따라 걸어서 `"Exif\0\0"`를 찾는다
  (바이트 검색으로 하면 픽셀 데이터에 우연히 있는 같은 바이트열이 걸린다). `II`/`MM` 양쪽 지원.
  파일 앞 **128KB만** 읽는다 — EXIF는 픽셀 데이터 앞에 있고, 12장을 통째로 메모리에 올릴 이유가 없다.
- **가둬 놓는 것** — TIFF 블록은 그 세그먼트 길이만큼 잘라낸 `DataView`로 읽는다. IFD는 값 오프셋을
  어디로든 돌릴 수 있어서, 파일 전체를 보는 뷰로 읽으면 손상된 블록이 **뒤따르는 세그먼트의 바이트를
  촬영 시각으로 내놓을 수 있다.** 뷰를 세그먼트에 가두면 같은 오프셋이 그냥 예외가 되고, 경계 검사를
  읽는 지점마다 흩뿌릴 필요도 없어진다.
- **타임존** — EXIF 촬영 시각에는 타임존이 없고, 있는 `OffsetTimeOriginal`(0x9011)은 일부러 무시한다.
  이걸 반영하면 도쿄에서 04:56에 찍은 사진이 콜라주를 만드는 곳의 시각으로 밀려서, 카메라가 보여준
  적 없는 시각이 캡션에 찍힌다. `formatStamp()`도 `datetime-local` 입력도 로컬 기준이다.
- **범위 밖** — HEIC/HEIF는 EXIF가 ISOBMFF item에 들어가는 다른 컨테이너라서 읽지 않는다.
  PNG, 그리고 APP13에 실리는 IPTC/XMP 날짜도 읽지 않는다. 전부 조용히 mtime으로 내려가고,
  사용자는 언제든 카드에서 직접 고칠 수 있다. HEIC는 픽셀과 촬영 시각이 별개의 문제라는 점만
  구분해 두면 된다 — Safari에서는 사진이 열리고 시각만 mtime으로 내려가지만, Chrome·Firefox
  에서는 픽셀부터 디코딩이 안 돼서 파일 자체가 건너뛰어진다(위 "못 여는 포맷" 참고).
- **개인정보** — EXIF에는 GPS도 들어 있다. 위 날짜 태그 셋(과 거기로 가는 포인터) 말고는 파싱조차
  하지 않고, 함수가 돌려줄 수 있는 것도 `Date`뿐이다. 내보내는 PNG에도 실리지 않는다 — 캔버스는
  픽셀 버퍼라 `drawImage` 시점에 컨테이너가 사라지고, 실제로 나온 청크는 `IHDR`/`IDAT`/`IEND`뿐이었다.

## SNS 공유

장마다 Instagram · Threads · X 버튼이 있다. 세 서비스 다 게시 API는 백엔드와 공개 이미지 URL을
요구하므로 쓰지 않는다 — 사진이 브라우저를 떠나는 순간 이 앱의 전제가 깨진다. 대신 브라우저가
그 환경에서 실제로 할 수 있는 것을 한다.

| | 조건 | 하는 일 |
|---|---|---|
| `share` | `navigator.canShare({files})` | OS 공유 시트. 여기서 앱을 고르면 그게 곧 업로드다 |
| `clipboard` | 시트 없음 · X/Threads | PNG를 클립보드에 넣고 `intent/post`를 연다. 붙여넣기 한 번 |
| `download` | 시트 없음 · Instagram, 또는 클립보드 불가 | PNG를 내려받고 컴포저를 연다 |

Instagram만 갈라지는 건 웹 컴포저가 파일 선택만 받기 때문이다 — 붙여넣기도, 인텐트 URL도 없다.
X와 Threads는 `?text=`로 문구를 미리 채운다(그 장에서 적은 문구들). 이미지를 URL로 실을 수 있는
서비스는 셋 중 없다. 데스크톱은 공유 시트가 있어도 Instagram·Threads·X가 OS에 등록돼 있지 않아
시트에 뜨지 않는다. 즉 `share`는 사실상 모바일 경로다.

분기는 `sharePlan()` 하나에 모여 있고, 기능 탐지 결과는 클릭 전에 이미 정해지므로 무엇이 일어날지
버튼 위에 미리 적어 둔다.

**공유본은 3077px이 아니라 1080px이다.** 두 가지 이유가 겹친다.

- Instagram이 2025년에 그리드를 3:4로 바꾸면서 1080×1440을 무크롭으로 받는다. 이 콜라주가 이미
  3077×4096 = 3:4다.
- `navigator.share()`는 클릭의 transient activation을 요구하는데, `ClipboardItem`과 달리 프로미스를
  받지 못한다. 핸들러 안에서 `await`를 하나라도 걸면 WebKit에서 `NotAllowedError`로 죽는다.
  그래서 blob은 클릭 **전에** 있어야 하고, 편집이 멎고 400ms 뒤(제스처 커밋과 같은 값) 미리 만들어
  둔다. 그 비용이 감당되는 게 1080이라서다 — 아래는 렌더 + 인코딩 실측(3회 중앙값, Chrome/macOS,
  `getImageData()`로 래스터화를 강제).

| 폭 | 래스터화 | PNG 인코딩 | 합계 | 용량 |
|---|---|---|---|---|
| 1080 × 1438 | 3ms | 29ms | 33ms | 99KB |
| 1440 × 1917 | 7ms | 41ms | 47ms | 138KB |
| 3077 × 4096 | 7ms | 186ms | 192ms | 478KB |

비용은 거의 전부 인코딩이고 픽셀 수를 따라간다. 내려받기는 3077px 그대로다.

(측정할 때 브라우저 탭이 백그라운드면 타이머가 1Hz로 클램프돼 전부 ~1초로 읽힌다. 폭을 바꿔도
값이 안 변하면 그걸 의심하면 된다.)

브랜드 아이콘은 인라인 SVG다. shadcn은 lucide를 쓰는데 lucide에는 브랜드 로고가 없어서 shadcn의
블록들도 직접 붙여 넣는다. 마크는 Simple Icons(CC0), 24 viewBox를 `currentColor`로 채운다.

## 구조

```
index.html        UI + 앱 로직
timeline.js       레이아웃 상수, 캡션 포맷, 미리보기 폭, EXIF 촬영 시각 파서, 못 여는 파일 안내,
                  공유 분기, 캔버스 렌더 (순수 함수)
timeline.test.mjs 실측값·EXIF·안내 문구·공유 분기 회귀 테스트
```

빌드 없음, 의존성 없음. 정적 파일 세 개가 전부다.

## 실행

```bash
python3 -m http.server 8123
```

`http://localhost:8123` 접속. (ES 모듈이라 `file://`로는 열리지 않는다.)

## 테스트

```bash
node --test timeline.test.mjs
```

레이아웃 기대값은 전부 원본 실측치다. 상수를 건드리면 여기서 깨진다.

EXIF 쪽은 픽스처 파일을 두지 않고 테스트 안에서 JPEG 바이트를 조립한다 — 바이너리 픽스처는 파서가
의존하는 오프셋을 전부 가리고, 정작 중요한 경우(빅엔디언, 잘린 헤더, 없는 태그)는 손에 있는 카메라가
만들어 주지 않는다. 유효한 파일의 바이트를 한 개씩 뒤집어 가며 `null`이나 정상 `Date`만 나오는지도
같이 확인한다.
