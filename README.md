# Timeline Grid

사진 여러 장에 각각 시각과 문구를 붙여, 하루의 흐름을 담은 타임라인 콜라주를 만들어 주는 웹 앱.

3×2 여섯 컷이 한 장(3077×4096)이고, 사진이 6장을 넘으면 자동으로 다음 장으로 넘어간다.
업로드·합성·저장이 전부 브라우저 안에서 끝나므로 사진은 어디로도 전송되지 않는다.

## 레이아웃

레이아웃은 눈대중이 아니라 원본에서 측정했다.
[instagram.com/p/Daz6IEyEpT5](https://www.instagram.com/p/Daz6IEyEpT5/) 캐러셀 12장(각 3077×4096)을
내려받아 흰 행·열을 스캔한 결과, 12장 전부 아래 값에서 일치했다 — 사람이 매번 배치한 게 아니라 고정 템플릿이다.

| 항목 | 실측값 (3077px 기준) |
|---|---|
| 캔버스 | 3077 × 4096 |
| 사진 행 top | 0 / 1347 / 2695 (pitch 1347.5) |
| 사진 셀 | 1538.5 × 1032, 좌우 여백 0, 열 간격 0 |
| 캡션 밴드 중심 | 행 top + 1193 (= 사진 하단 + 161) |
| 캡션 | Tinos 45px, 행간 50px, 열 중앙 정렬 |
| 캡션 잉크 상자 | 445 × 42 (`04:56, Thursday, July 09`) |

`timeline.js`의 `SPEC`이 이 값들을 캔버스 폭 대비 비율로 들고 있다.

## 캡션 폰트

캡션 폰트는 7종에서 고를 수 있고, 그중 넷은 한글 글리프를 가진다.

| 폰트 | 한글 | 정규화 크기 |
|---|---|---|
| Tinos (기본 · 원본) | | 45.3px |
| EB Garamond | | 47.8px |
| Lora | | 40.5px |
| 본명조 Noto Serif KR | O | 39.2px |
| 고운바탕 Gowun Batang | O | 41.9px |
| 나눔명조 Nanum Myeongjo | O | 41.4px |
| 본고딕 Noto Sans KR | O | 40.4px |

폰트별 상수 표는 두지 않는다. 렌더할 때마다 `ctx.measureText()`로 기준 문자열(원본 첫 컷 캡션
`04:56, Thursday, July 09`)의 잉크 폭과 ascent/descent를 실측해서 세 가지를 유도한다.

- **크기** — 잉크 폭이 원본의 445px가 되도록 맞춘다. Tinos는 원래 값인 45px 부근으로 돌아온다.
- **위치** — 실측 ascent/descent로 baseline을 역산해, 잉크 밴드 중심을 행 top + 1193에 놓는다.
- **행간** — 잉크 높이 + 0.2em. 원본의 50px는 Tinos 잉크 0.911em에서 나온 이 규칙의 특수해다.
  50px로 고정하면 잉크가 1.08em인 본명조는 두 줄 간격이 1.4px까지 좁아진다.

기준 문자열을 고정하는 것이 핵심이다. 캡션마다 실측하면 한 행에 나란히 놓인 영문 캡션과 한글
캡션의 baseline이 서로 어긋난다. 원본 12장이 전부 같은 위치였다는 건 고정 baseline이었다는 뜻이다.
한글은 디센더가 없어 잉크 중심이 2~4px 위로 올라가는데, 모든 캡션이 같이 올라가므로 정렬은 유지된다.

한글 폰트의 Google Fonts CSS는 58~98KB(한글이 unicode-range 서브셋 90~124개로 쪼개져 있다)라서
`<link>`는 폰트를 고를 때 주입하고, `document.fonts.load(spec, text)`에 캡션 텍스트를 넘겨
필요한 서브셋만 내려받는다. 캔버스는 CSS처럼 글리프별 fallback을 해주지 않으므로 이 순서가 중요하다.

(정규화 크기는 Chrome / macOS 실측값이다. 폰트 렌더러에 따라 소수점은 조금 달라진다.)

## 미리보기 해상도

미리보기 캔버스는 CSS로 컨테이너 폭까지 늘어나므로(`width: 100%`), 비트맵은 **화면에 실제로 찍히는
디바이스 픽셀 수**여야 한다. `previewWidth(cssW, dpr)`가 그 값을 만들고, 컨테이너 폭은 캔버스를
DOM에 넣은 뒤 한 번만 잰다(모든 장이 같은 폭이다).

고정 620px이던 시절 Chrome/macOS DPR 2에서 잰 값:

| 창 | 캔버스 CSS 폭 | 620px 비트맵의 확대율 | 현재 비트맵 | 현재 확대율 |
|---|---|---|---|---|
| 데스크톱 (`.wrap` 1040 상한) | 962 | 3.10× | 1924 | 1.000× |
| 좁은 창 | 622 | 2.01× | 1244 | 1.000× |
| 모바일 375px | 313 | 1.01× | 626 | 1.000× |

CSS 폭만 보면 1.0배 근처라 멀쩡해 보이는 게 함정이었다. 흐림은 CSS 크기가 아니라 HiDPI에서 왔다.

폭이 3.1배가 되면 픽셀 수는 9.6배지만, 문구를 한 글자 칠 때마다 도는 `drawPages()`는
사진 12장(2장 분량) 기준으로 이 정도다 — 11회 중앙값, `getImageData()`로 래스터화를 강제한 값.

| 비트맵 폭 | 핸들러 동기 시간 | 래스터화까지 |
|---|---|---|
| 620 (이전) | 0.9ms | 2.2ms |
| 1924 (데스크톱) | 1.7ms | 4.9ms |
| 626 (모바일) | 1.2ms | 2.8ms |

한 프레임(16.7ms) 안에 여유 있게 들어와서 디바운스도, 입력 중 저해상도 렌더도 넣지 않았다.
DPR 3 폰이라도 313 × 3 = 939px로 데스크톱보다 작아서 모바일 상한도 두지 않았다.
상한은 내보내기 폭(3077)에만 걸어 둔다. 컨테이너가 962 CSS px를 넘지 않으므로 DPR 3.2부터 닿는다.

캡션 위치는 폭을 바꿔도 그대로다. 620 / 1282 / 1924 / 3077에서 렌더한 뒤 흰 행 스캔으로 잉크 밴드를
재고 3077 기준으로 환산했을 때, 밴드 중심과 `행 top + 1193` 사이의 오차는 Tinos가 ±2px,
본명조 + 한글 캡션이 −2~−6px으로 **모든 폭에서 같았다.** 한글 쪽 상수 오프셋은 기준 문자열이 라틴
문자열로 고정돼 있어 생기는 원래 성질이고(위 "캡션 폰트" 참고), 해상도와는 무관하다.

## 구조

```
index.html        UI + 앱 로직
timeline.js       레이아웃 상수, 캡션 포맷, 캔버스 렌더 (순수 함수)
timeline.test.mjs 실측값 회귀 테스트
```

빌드 없음, 의존성 없음. 정적 파일 세 개가 전부다.

## 실행

```bash
python3 -m http.server 8123
```

`http://localhost:8123` 접속. (ES 모듈이라 `file://`로는 열리지 않는다.)

## 테스트

```bash
node --test timeline.test.mjs
```

기대값은 전부 원본 실측치다. 레이아웃 상수를 건드리면 여기서 깨진다.
